1. Product definition

1.1 Vision

AgencyOS is a configurable operating system for marketing agencies. It connects
the complete lifecycle:

Lead → deal → client onboarding → campaign/project delivery → approval →
reporting → invoice → renewal

Every contact, decision, task, asset, approval, hour, expense, result, and
relationship should belong to one coherent workspace data graph. It should feel
custom-built for each agency without requiring that agency to write code.

1.2 Product principles

1. Strong defaults, deep configuration, controlled complexity.
2. Agency-native concepts: retainers, campaigns, deliverables, client
approvals, billable work, capacity, profitability, and recurring reporting.
3. Database-enforced tenant isolation.
4. Least privilege and explicit internal/client visibility.
5. Collaboration for employees, contractors, clients, and reviewers.
6. Progressive disclosure: simple for a small agency, powerful for operations
teams.
7. Extensible through custom fields, views, templates, workflows, webhooks, and
APIs.
8. Auditable changes, especially permissions, approvals, exports, and finance.
9. Fast keyboard-friendly daily use.
10. Accessible, mobile-responsive, and trustworthy.

1.3 Target customers and personas

• Founder/owner: pipeline, revenue, margin, health, risk, and utilization.
• Sales/account executive: leads, deals, activities, follow-up, forecasting.
• Account manager: Client 360, requests, communication, renewals, reports.
• Project/traffic manager: work intake, schedules, dependencies, capacity.
• Strategist/creative/specialist: assigned work, briefs, files, feedback, time.
• Finance/operations: retainers, budgets, rates, costs, invoices, exports.
• Contractor: restricted project/task access.
• Client stakeholder: portal, requests, files, approvals, reports.
• Workspace admin: members, teams, roles, configuration, integrations, audit.

1.4 Commercial quality bar

The experience must justify a premium implementation:

• Fast onboarding with realistic templates and demo data.
• Elegant information density, not a generic admin dashboard.
• Cross-linked records and a complete activity history.
• Configurable terminology, fields, statuses, pipelines, views, and branding.
• Safe external collaboration and client approval.
• Useful operational intelligence, not vanity charts.
• Excellent search, keyboard interaction, bulk actions, and saved views.
• Clear permission and audit behavior.

7. Tenant, identity, roles, and invitations

7.1 Tenancy rules

• A person has one Supabase Auth identity and may belong to many workspaces.
• Every tenant-owned record has a non-null workspace_id.
• URL workspace slugs are resolved server-side; browser-supplied workspace IDs
are never trusted.
• A workspace member may have role assignments and team memberships.
• Client contacts are not automatically internal members.
• Service-role operations are isolated to small server-only modules.
• All cross-entity relationships must belong to the same workspace, enforced by
constraints or triggers, not application convention.

7.2 Default roles

• Owner
• Administrator
• Operations
• Sales
• Account Manager
• Team Member
• Contractor
• Finance
• Client
• Guest Reviewer

Roles are workspace-specific. Owner is protected from accidental removal.
Custom roles are allowed. A user can hold multiple roles; permissions combine,
while explicit data visibility remains restrictive.

7.4 Invitation lifecycle

1. Authorized member enters email, role(s), optional team(s), and expiry.
2. Server normalizes email, checks seat/policy rules, and creates one invitation
transactionally.
3. Store only a cryptographic hash of the bearer token.
4. Send through an email adapter; local development writes to a capture inbox.
5. Recipient signs in or signs up.
6. Acceptance validates token hash, normalized email, expiry, revocation,
existing membership, and inviter authorization.
7. Membership/role/team creation and invite consumption happen atomically.
8. Emit audit and notification events.
9. Admin may resend with token rotation or revoke.

Prevent invite replay, privilege escalation, duplicate membership, email-case
bugs, and timing-dependent partial acceptance.

8. Database contract

8.1 Common conventions

Use UUID primary keys (gen_random_uuid()), timestamptz, snake_case, and:

```text
id uuid primary key
workspace_id uuid not null        -- on every tenant-owned table
created_at timestamptz not null default now()
updated_at timestamptz not null default now()
created_by uuid null
updated_by uuid null
archived_at timestamptz null      -- where archival is useful
version integer not null default 1 -- approval/concurrency-sensitive records
```

Use database enums only for genuinely stable states. Use lookup/config tables
for workspace-customizable statuses. Add:

• foreign keys and deliberate deletion behavior;
• unique constraints scoped to workspace;
• indexes beginning with workspace_id;
• indexes for foreign keys, frequent filters, status, due date, assignee, and
full-text search;
• checks for nonnegative quantities and valid date/order ranges;
• automatic updated_at;
• same-workspace relationship guards;
• normalized searchable email/domain fields where applicable.

Money uses integer minor units plus ISO currency code. Durations use integer
minutes. Store display time zone as an IANA identifier.

8.9 Search and event model

Create a permission-aware global search across contacts, companies, leads,
deals, clients, projects, tasks, campaigns, deliverables, and knowledge. Start
with Postgres full-text/trigram search and a unified indexed search document
projection. Never return a result the caller cannot open.

Domain mutations should emit transactional outbox events:

• stable event ID and type;
• workspace, actor, entity, version, timestamp, and safe payload;
• idempotent consumers;
• retry/backoff and dead-letter visibility;
• no sensitive credentials in payloads.

Use events for activity, notifications, automation, webhook delivery, and search
projection without making user-facing transactions depend on external services.

9. Supabase security contract

9.1 Client/session architecture

• Browser: createBrowserClient from @supabase/ssr.
• Server: a new request-scoped createServerClient using the framework cookie
API; never share a mutable server client globally.
• Next.js 16: use proxy.ts to refresh auth cookies where required.
• Apply current Supabase SSR cache-control behavior so responses that set auth
cookies cannot be cached and served across users.
• On protected server work, validate the user against Supabase Auth; do not
authorize from an unverified browser payload.
• Validate next redirects as local allow-listed paths. Reject protocol-relative
and external URLs.
• Keep secret/service keys in server-only modules with import guards.

9.2 Private authorization helpers

Create a non-exposed private schema with carefully reviewed
security definer helpers, for example:

```sql
private.is_workspace_member(target_workspace_id uuid)
private.has_permission(target_workspace_id uuid, permission_key text)
private.can_access_client(target_client_id uuid)
private.can_access_project(target_project_id uuid)
private.can_access_entity(target_type text, target_id uuid)
```

Each definer function must:

• set an explicit safe search_path;
• schema-qualify referenced objects;
• avoid user-controlled dynamic SQL;
• be owned by a non-login privileged role where supported;
• revoke execution from public and grant only what is necessary;
• avoid recursive RLS policy evaluation;
• return false for unauthenticated, suspended, or cross-workspace requests.

9.3 RLS invariants

Enable RLS on every exposed table, including lookup/config tables containing
workspace data. Policies must cover select, insert, update, and delete
deliberately.

Every tenant policy must enforce:

1. The authenticated caller is an active member of the row’s workspace.
2. The caller has the required action permission.
3. The caller satisfies entity visibility rules.
4. with check prevents changing workspace_id, owner, or protected state to
escape authorization.

Client/guest policies additionally require an explicit portal/client grant.
Contractor access should be restricted to assigned/shared projects where the
role policy requires it.

Never treat hidden navigation, a disabled button, or a Server Component as an
authorization boundary. Re-check permission in the server command/database.

9.4 Database API hardening

• Audit table/function grants as well as RLS.
• Revoke unnecessary default privileges from anon and authenticated.
• Expose only required schemas through the data API.
• Keep internal tables/functions in private schemas.
• Do not expose arbitrary security definer RPCs.
• Add rate/size limits and authorization to exports and file signing.
• Use server-only service-role access only for trusted jobs that cannot operate
under a user token.

9.5 Relationship integrity

For every reference between tenant-owned rows, ensure the child and parent have
the same workspace_id. Use composite foreign keys or deferrable constraint
triggers. Cover both insert and update. Include tests attempting to connect
records from two workspaces.

9.6 Storage

Use private buckets:

```text
workspace-assets
avatars
imports
exports
```

Paths must be non-guessable and begin with the authorized workspace identifier
where tenant-owned. Add RLS policies on storage.objects for read/upload/update/
delete. Validate object ownership and linked entity access. Use short-lived
signed URLs. Validate file size and MIME using server-observed metadata; do not
trust extensions. Track scan status and prevent client-visible use until safe.
Exports expire and are deleted by a scheduled cleanup.

9.7 Required negative security tests

Using two workspaces, internal users, a contractor, a client user, a suspended
member, and unauthenticated access, prove that:

• no table leaks rows across workspaces;
• guessed UUIDs and modified slugs fail;
• inserts cannot claim another workspace;
• updates cannot move rows between workspaces;
• cross-workspace foreign keys fail;
• unauthorized role/member changes fail;
• a user cannot grant permissions they are not allowed to manage;
• client users cannot read internal comments/files/finance;
• contractor access is limited as configured;
• invitation tokens cannot be replayed or accepted by another email;
• signed URLs cannot be issued without entity access;
• search, exports, notifications, realtime channels, and reports do not leak;
• service-role modules cannot enter the client bundle.

11. Core workflows and acceptance criteria

11.1 New agency

1. User signs up and verifies.
2. Creates workspace with name, slug, currency, time zone.
3. Atomic transaction creates owner membership, default roles/permissions,
statuses, pipeline, templates, dashboard, and feature flags.
4. User lands in guided onboarding and may load demo data.

Pass when partial failure leaves no orphaned workspace and another workspace
cannot observe any created data.

11.2 Invite colleague

Owner invites a teammate with role/team. Recipient accepts using the invited
email, joins the workspace, and sees only allowed navigation and records. Resend,
expiry, revoke, duplicate, changed-email, and replay behavior must be tested.

11.3 Lead to revenue

Import or create lead → qualify → associate contact/company → create deal →
advance stage with activity logging → mark won → invoke an idempotent onboarding
command that creates/links client, project from template, onboarding tasks, and
activity/audit events.

11.4 Delivery and approval

Create project → assign task → upload deliverable version → request approval →
client receives safe notification and opens portal → approve or request changes
→ immutable decision appears internally and externally according to visibility.
New version requires new approval.

11.5 Time and profitability

Member records billable/nonbillable time → submits timesheet → manager approves
→ budget burn, utilization, and projected margin update. Unauthorized users
cannot view costs or organization-wide time.

11.6 Customization

Admin adds a custom field, adds it to a form/list, enters valid data, filters and
exports it. Invalid values fail on both server and database-compatible
validation. Removing a definition is archival and does not silently destroy
historic data.

11.7 Import/export

Upload CSV → preview → map fields → validate → execute idempotently → report
created/updated/skipped/error rows → download error CSV. Export respects current
filters, selected columns, field-level sensitivity, permissions, and audit log.

11.8 Portal isolation

Client user sees explicitly shared records for their client only. They never see
internal comments, costs, other clients, workspace settings, unpublished
reports, or unshared files. Direct URL guessing and search must fail.

12. Realtime, jobs, email, and integrations

12.1 Realtime

Use Supabase Realtime for notification count, comments, relevant record changes,
and optional presence. Authorize private channels. Always refetch through normal
RLS-protected queries; realtime payloads are hints, not the source of truth.

12.2 Background jobs

Use a Postgres-native queue/outbox approach with:

• idempotency keys and unique constraints;
• explicit attempt count and exponential backoff;
• visibility timeout/lease;
• max attempts and dead-letter state;
• structured error summaries;
• operator-visible run history;
• scheduled sweeps for stuck work.

Use Supabase Cron for scheduled reports, reminders, recurring tasks, webhook
retries, cleanup, and queue invocation. Keep secrets in Vault/server
environment, never in job payloads.

12.3 Email

Define a provider-neutral interface. Local/test adapter captures messages for
assertions. Templates:

• invite;
• magic link/auth handled appropriately by Supabase;
• mention;
• assignment;
• approaching/overdue task;
• approval requested/decided;
• weekly digest;
• report ready.

Every email honors tenant branding, user preferences, audience visibility, and
safe deep links. Do not send email within an open database transaction.

12.4 External integrations

Use adapters and connection records. OAuth credentials/tokens are encrypted or
referenced through a secret store, never returned to the browser or logged.
Normalize provider webhooks to internal events. Include deterministic mocks for
local/test. A missing external account must not break core CRM functionality.

14. Performance, reliability, and observability

• Server-side pagination; never fetch whole tenant tables for lists.
• URL-backed table filter/sort/view state.
• Avoid N+1 queries and unbounded relation expansion.
• Add query indexes based on real access patterns and inspect representative
plans.
• Use optimistic UI only when conflicts and rollback are handled.
• Use version checks for concurrent approval/configuration edits.
• Dynamic authenticated responses must not enter a shared cache.
• Health endpoint reports application readiness without leaking secrets.
• Structured logs include request/correlation ID, workspace when safe, actor,
action, latency, and result; redact tokens, credentials, message bodies, and
sensitive personal data.
• Capture server/client exceptions through an adapter that is a no-op locally.
• Track audit events separately from debug logs.
• Provide runbooks for migrations, stuck jobs, webhook replay, invite problems,
storage incidents, tenant leakage response, and restore validation.

Initial performance targets under representative seeded data:

• common authenticated navigation: useful response within 1 second on a normal
development connection, excluding cold start;
• filtered list queries: p95 database execution target under 300 ms;
• command feedback: visible within 500 ms where no external provider is needed;
• public pages: strong Core Web Vitals and no unnecessary client JavaScript.

Do not falsify benchmarks. Record the environment and dataset used.

Supabase RLS, grants, RBAC, and storage

Official references:

• RLS:
https://supabase.com/docs/guides/database/postgres/row-level-security

https://supabase.com/docs/guides/api/custom-claims-and-role-based-access-control-rbac

• Storage access:
https://supabase.com/docs/guides/storage/security/access-control

Rules:
