    72→1. Product definition
    73→
    74→1.1 Vision
    75→
    76→AgencyOS is a configurable operating system for marketing agencies. It connects
    77→the complete lifecycle:
    78→
    79→Lead → deal → client onboarding → campaign/project delivery → approval →
    80→reporting → invoice → renewal
    81→
    82→Every contact, decision, task, asset, approval, hour, expense, result, and
    83→relationship should belong to one coherent workspace data graph. It should feel
    84→custom-built for each agency without requiring that agency to write code.
    85→
    86→1.2 Product principles
    87→
    88→1. Strong defaults, deep configuration, controlled complexity.
    89→2. Agency-native concepts: retainers, campaigns, deliverables, client
    90→approvals, billable work, capacity, profitability, and recurring reporting.
    91→3. Database-enforced tenant isolation.
    92→4. Least privilege and explicit internal/client visibility.
    93→5. Collaboration for employees, contractors, clients, and reviewers.
    94→6. Progressive disclosure: simple for a small agency, powerful for operations
    95→teams.
    96→7. Extensible through custom fields, views, templates, workflows, webhooks, and
    97→APIs.
    98→8. Auditable changes, especially permissions, approvals, exports, and finance.
    99→9. Fast keyboard-friendly daily use.
   100→10. Accessible, mobile-responsive, and trustworthy.
   101→
   102→1.3 Target customers and personas
   103→
   104→• Founder/owner: pipeline, revenue, margin, health, risk, and utilization.
   105→• Sales/account executive: leads, deals, activities, follow-up, forecasting.
   106→• Account manager: Client 360, requests, communication, renewals, reports.
   107→• Project/traffic manager: work intake, schedules, dependencies, capacity.
   108→• Strategist/creative/specialist: assigned work, briefs, files, feedback, time.
   109→• Finance/operations: retainers, budgets, rates, costs, invoices, exports.
   110→• Contractor: restricted project/task access.
   111→• Client stakeholder: portal, requests, files, approvals, reports.
   112→• Workspace admin: members, teams, roles, configuration, integrations, audit.
   113→
   114→1.4 Commercial quality bar
   115→
   116→The experience must justify a premium implementation:
   117→
   118→• Fast onboarding with realistic templates and demo data.
   119→• Elegant information density, not a generic admin dashboard.
   120→• Cross-linked records and a complete activity history.
   121→• Configurable terminology, fields, statuses, pipelines, views, and branding.
   122→• Safe external collaboration and client approval.
   123→• Useful operational intelligence, not vanity charts.
   124→• Excellent search, keyboard interaction, bulk actions, and saved views.
   125→• Clear permission and audit behavior.

   452→7. Tenant, identity, roles, and invitations
   453→
   454→7.1 Tenancy rules
   455→
   456→• A person has one Supabase Auth identity and may belong to many workspaces.
   457→• Every tenant-owned record has a non-null workspace_id.
   458→• URL workspace slugs are resolved server-side; browser-supplied workspace IDs
   459→are never trusted.
   460→• A workspace member may have role assignments and team memberships.
   461→• Client contacts are not automatically internal members.
   462→• Service-role operations are isolated to small server-only modules.
   463→• All cross-entity relationships must belong to the same workspace, enforced by
   464→constraints or triggers, not application convention.
   465→
   466→7.2 Default roles
   467→
   468→• Owner
   469→• Administrator
   470→• Operations
   471→• Sales
   472→• Account Manager
   473→• Team Member
   474→• Contractor
   475→• Finance
   476→• Client
   477→• Guest Reviewer
   478→
   479→Roles are workspace-specific. Owner is protected from accidental removal.
   480→Custom roles are allowed. A user can hold multiple roles; permissions combine,
   481→while explicit data visibility remains restrictive.

   511→7.4 Invitation lifecycle
   512→
   513→1. Authorized member enters email, role(s), optional team(s), and expiry.
   514→2. Server normalizes email, checks seat/policy rules, and creates one invitation
   515→transactionally.
   516→3. Store only a cryptographic hash of the bearer token.
   517→4. Send through an email adapter; local development writes to a capture inbox.
   518→5. Recipient signs in or signs up.
   519→6. Acceptance validates token hash, normalized email, expiry, revocation,
   520→existing membership, and inviter authorization.
   521→7. Membership/role/team creation and invite consumption happen atomically.
   522→8. Emit audit and notification events.
   523→9. Admin may resend with token rotation or revoke.
   524→
   525→Prevent invite replay, privilege escalation, duplicate membership, email-case
   526→bugs, and timing-dependent partial acceptance.

   530→8. Database contract
   531→
   532→8.1 Common conventions
   533→
   534→Use UUID primary keys (gen_random_uuid()), timestamptz, snake_case, and:
   535→
   536→```text
   537→id uuid primary key
   538→workspace_id uuid not null        -- on every tenant-owned table
   539→created_at timestamptz not null default now()
   540→updated_at timestamptz not null default now()
   541→created_by uuid null
   542→updated_by uuid null
   543→archived_at timestamptz null      -- where archival is useful
   544→version integer not null default 1 -- approval/concurrency-sensitive records
   545→```
   546→
   547→Use database enums only for genuinely stable states. Use lookup/config tables
   548→for workspace-customizable statuses. Add:
   549→
   550→• foreign keys and deliberate deletion behavior;
   551→• unique constraints scoped to workspace;
   552→• indexes beginning with workspace_id;
   553→• indexes for foreign keys, frequent filters, status, due date, assignee, and
   554→full-text search;
   555→• checks for nonnegative quantities and valid date/order ranges;
   556→• automatic updated_at;
   557→• same-workspace relationship guards;
   558→• normalized searchable email/domain fields where applicable.
   559→
   560→Money uses integer minor units plus ISO currency code. Durations use integer
   561→minutes. Store display time zone as an IANA identifier.
   562→
   563→8.2 Identity and configuration tables
   564→
   565→Implement:
   566→
   567→• profiles(user_id, display_name, avatar_path, locale, timezone)
   568→• workspaces(name, slug, timezone, currency, locale, logo_path, settings_json)
   569→• workspace_memberships(workspace_id, user_id, status, title, joined_at)
   570→• roles(workspace_id, name, description, is_system)
   571→• permissions(key, description)
   572→• role_permissions(role_id, permission_id)
   573→• membership_roles(membership_id, role_id)
   574→• teams(workspace_id, name, description)
   575→• team_memberships(team_id, membership_id)
   576→• invitations(workspace_id, email_normalized, token_hash, expires_at, accepted_at, revoked_at, invited_by)
   577→• invitation_roles(invitation_id, role_id)
   578→• invitation_teams(invitation_id, team_id)
   579→• feature_flags(workspace_id, key, enabled, config_json)
   580→• workspace_preferences(workspace_id, user_id, preferences_json)
   581→• audit_events(workspace_id, actor_user_id, action, entity_type, entity_id, before_json, after_json, ip_hash, user_agent_summary, occurred_at)
   582→
   583→Audit events are append-only to ordinary users.

   722→9. Supabase security contract
   723→
   724→9.1 Client/session architecture
   725→
   726→• Browser: createBrowserClient from @supabase/ssr.
   727→• Server: a new request-scoped createServerClient using the framework cookie
   728→API; never share a mutable server client globally.
   729→• Next.js 16: use proxy.ts to refresh auth cookies where required.
   730→• Apply current Supabase SSR cache-control behavior so responses that set auth
   731→cookies cannot be cached and served across users.
   732→• On protected server work, validate the user against Supabase Auth; do not
   733→authorize from an unverified browser payload.
   734→• Validate next redirects as local allow-listed paths. Reject protocol-relative
   735→and external URLs.
   736→• Keep secret/service keys in server-only modules with import guards.
   737→
   738→9.2 Private authorization helpers
   739→
   740→Create a non-exposed private schema with carefully reviewed
   741→security definer helpers, for example:
   742→
   743→```sql
   744→private.is_workspace_member(target_workspace_id uuid)
   745→private.has_permission(target_workspace_id uuid, permission_key text)
   746→private.can_access_client(target_client_id uuid)
   747→private.can_access_project(target_project_id uuid)
   748→private.can_access_entity(target_type text, target_id uuid)
   749→```
   750→
   751→Each definer function must:
   752→
   753→• set an explicit safe search_path;
   754→• schema-qualify referenced objects;
   755→• avoid user-controlled dynamic SQL;
   756→• be owned by a non-login privileged role where supported;
   757→• revoke execution from public and grant only what is necessary;
   758→• avoid recursive RLS policy evaluation;
   759→• return false for unauthenticated, suspended, or cross-workspace requests.
   760→
   761→9.3 RLS invariants
   762→
   763→Enable RLS on every exposed table, including lookup/config tables containing
   764→workspace data. Policies must cover select, insert, update, and delete
   765→deliberately.
   766→
   767→Every tenant policy must enforce:
   768→
   769→1. The authenticated caller is an active member of the row’s workspace.
   770→2. The caller has the required action permission.
   771→3. The caller satisfies entity visibility rules.
   772→4. with check prevents changing workspace_id, owner, or protected state to
   773→escape authorization.
   774→
   775→Client/guest policies additionally require an explicit portal/client grant.
   776→Contractor access should be restricted to assigned/shared projects where the
   777→role policy requires it.
   778→
   779→Never treat hidden navigation, a disabled button, or a Server Component as an
   780→authorization boundary. Re-check permission in the server command/database.
   781→
   782→9.4 Database API hardening
   783→
   784→• Audit table/function grants as well as RLS.
   785→• Revoke unnecessary default privileges from anon and authenticated.
   786→• Expose only required schemas through the data API.
   787→• Keep internal tables/functions in private schemas.
   788→• Do not expose arbitrary security definer RPCs.
   789→• Add rate/size limits and authorization to exports and file signing.
   790→• Use server-only service-role access only for trusted jobs that cannot operate
   791→under a user token.
   792→
   793→9.5 Relationship integrity
   794→
   795→For every reference between tenant-owned rows, ensure the child and parent have
   796→the same workspace_id. Use composite foreign keys or deferrable constraint
   797→triggers. Cover both insert and update. Include tests attempting to connect
   798→records from two workspaces.
   799→
   800→9.6 Storage
   801→
   802→Use private buckets:
   803→
   804→```text
   805→workspace-assets
   806→avatars
   807→imports
   808→exports
   809→```
   810→
   811→Paths must be non-guessable and begin with the authorized workspace identifier
   812→where tenant-owned. Add RLS policies on storage.objects for read/upload/update/
   813→delete. Validate object ownership and linked entity access. Use short-lived
   814→signed URLs. Validate file size and MIME using server-observed metadata; do not
   815→trust extensions. Track scan status and prevent client-visible use until safe.
   816→Exports expire and are deleted by a scheduled cleanup.
   817→
   818→9.7 Required negative security tests
   819→
   820→Using two workspaces, internal users, a contractor, a client user, a suspended
   821→member, and unauthenticated access, prove that:
   822→
   823→• no table leaks rows across workspaces;
   824→• guessed UUIDs and modified slugs fail;
   825→• inserts cannot claim another workspace;
   826→• updates cannot move rows between workspaces;
   827→• cross-workspace foreign keys fail;
   828→• unauthorized role/member changes fail;
   829→• a user cannot grant permissions they are not allowed to manage;
   830→• client users cannot read internal comments/files/finance;
   831→• contractor access is limited as configured;
   832→• invitation tokens cannot be replayed or accepted by another email;
   833→• signed URLs cannot be issued without entity access;
   834→• search, exports, notifications, realtime channels, and reports do not leak;
   835→• service-role modules cannot enter the client bundle.

   956→11. Core workflows and acceptance criteria
   957→
   958→11.1 New agency
   959→
   960→1. User signs up and verifies.
   961→2. Creates workspace with name, slug, currency, time zone.
   962→3. Atomic transaction creates owner membership, default roles/permissions,
   963→statuses, pipeline, templates, dashboard, and feature flags.
   964→4. User lands in guided onboarding and may load demo data.
   965→
   966→Pass when partial failure leaves no orphaned workspace and another workspace
   967→cannot observe any created data.
   968→
   969→11.2 Invite colleague
   970→
   971→Owner invites a teammate with role/team. Recipient accepts using the invited
   972→email, joins the workspace, and sees only allowed navigation and records. Resend,
   973→expiry, revoke, duplicate, changed-email, and replay behavior must be tested.
   974→
   975→11.3 Lead to revenue
   976→
   977→Import or create lead → qualify → associate contact/company → create deal →
   978→advance stage with activity logging → mark won → invoke an idempotent onboarding
   979→command that creates/links client, project from template, onboarding tasks, and
   980→activity/audit events.
   981→
   982→11.4 Delivery and approval
   983→
   984→Create project → assign task → upload deliverable version → request approval →
   985→client receives safe notification and opens portal → approve or request changes
   986→→ immutable decision appears internally and externally according to visibility.
   987→New version requires new approval.
   988→
   989→11.5 Time and profitability
   990→
   991→Member records billable/nonbillable time → submits timesheet → manager approves
   992→→ budget burn, utilization, and projected margin update. Unauthorized users
   993→cannot view costs or organization-wide time.
   994→
   995→11.6 Customization
   996→
   997→Admin adds a custom field, adds it to a form/list, enters valid data, filters and
   998→exports it. Invalid values fail on both server and database-compatible
   999→validation. Removing a definition is archival and does not silently destroy
  1000→historic data.

  1002→11.7 Import/export
  1003→
  1004→Upload CSV → preview → map fields → validate → execute idempotently → report
  1005→created/updated/skipped/error rows → download error CSV. Export respects current
  1006→filters, selected columns, field-level sensitivity, permissions, and audit log.

  1008→11.8 Portal isolation
  1009→
  1010→Client user sees explicitly shared records for their client only. They never see
  1011→internal comments, costs, other clients, workspace settings, unpublished
  1012→reports, or unshared files. Direct URL guessing and search must fail.

  1033→• operator-visible run history;
  1034→• scheduled sweeps for stuck work.
  1035→
  1036→Use Supabase Cron for scheduled reports, reminders, recurring tasks, webhook
  1037→retries, cleanup, and queue invocation. Keep secrets in Vault/server

  1094→14. Performance, reliability, and observability
  1095→
  1096→• Server-side pagination; never fetch whole tenant tables for lists.
  1097→• URL-backed table filter/sort/view state.
  1098→• Avoid N+1 queries and unbounded relation expansion.
  1099→• Add query indexes based on real access patterns and inspect representative
  1100→plans.
  1101→• Use optimistic UI only when conflicts and rollback are handled.
  1102→• Use version checks for concurrent approval/configuration edits.
  1103→• Dynamic authenticated responses must not enter a shared cache.
  1104→• Health endpoint reports application readiness without leaking secrets.
  1105→• Structured logs include request/correlation ID, workspace when safe, actor,
  1106→action, latency, and result; redact tokens, credentials, message bodies, and
  1107→sensitive personal data.
  1108→• Capture server/client exceptions through an adapter that is a no-op locally.
  1109→• Track audit events separately from debug logs.
  1110→• Provide runbooks for migrations, stuck jobs, webhook replay, invite problems,
  1111→storage incidents, tenant leakage response, and restore validation.
  1112→
  1113→Initial performance targets under representative seeded data:
  1114→
  1115→• common authenticated navigation: useful response within 1 second on a normal
  1116→development connection, excluding cold start;
  1117→• filtered list queries: p95 database execution target under 300 ms;
  1118→• command feedback: visible within 500 ms where no external provider is needed;
  1119→• public pages: strong Core Web Vitals and no unnecessary client JavaScript.
  1120→
  1121→Do not falsify benchmarks. Record the environment and dataset used.

  1402→Rules:
  1403→
  1404→• Separate authentication, session management, and authorization.
  1405→• Centralize authorization in a data-access/server-command layer; UI gating is
  1406→only presentation.
  1407→• Treat Server Actions and Route Handlers as externally callable endpoints.
  1408→• Re-authorize every mutation close to the data.
  1409→• Avoid returning whole records when the caller needs a small safe DTO.
  1410→• Protect against unsafe redirects and accidental client imports of server code.
  1411→• In Next.js 16 use the current proxy convention where framework auth refresh
  1412→requires it.

  1416→Official references:
  1417→
  1418→• SSR: https://supabase.com/docs/guides/auth/server-side
  1419→• SSR client:
  1420→https://supabase.com/docs/guides/auth/server-side/creating-a-client
  1421→• Advanced SSR:
  1422→https://supabase.com/docs/guides/auth/server-side/advanced-guide
  1423→• Server package choice:
  1424→https://supabase.com/docs/guides/auth/choosing-a-server-package
  1425→• Auth-helper migration:
  1426→https://supabase.com/docs/guides/troubleshooting/how-to-migrate-from-supabase-auth-helpers-to-ssr-package-5NRunM

  1428→Rules:
  1429→
  1430→• Use @supabase/ssr; legacy auth helpers are deprecated.
  1431→• Use separate browser and request-scoped server clients.
  1432→• Cookie-based SSR needs token refresh coordinated through server cookies.
  1433→• Current @supabase/ssr passes cache-control information when setting auth
  1434→cookies; preserve it to prevent a CDN from caching and serving one user’s auth
  1435→response to another.
  1436→• Cookie SSR chooses @supabase/ssr; bearer-token API servers may use the
  1437→dedicated server package where appropriate; the base client remains
  1438→@supabase/supabase-js.

  1440→Supabase RLS, grants, RBAC, and storage
  1441→
  1442→Official references:
  1443→
  1444→• RLS:
  1445→https://supabase.com/docs/guides/database/postgres/row-level-security
  1446→• RBAC/custom claims:
  1447→https://supabase.com/docs/guides/api/custom-claims-and-role-based-access-control-rbac
  1448→• Data API hardening:
  1449→https://supabase.com/docs/guides/api/securing-your-api
  1450→• Storage access:
  1451→https://supabase.com/docs/guides/storage/security/access-control
  1452→
  1453→Rules:
  1454→
  1455→• Enable RLS on exposed tables and write explicit action policies.
  1456→• RLS and SQL grants are complementary; RLS alone is not the whole API security
  1457→model.
  1458→• Review schema exposure, table/function grants, and default privileges.
  1459→• JWT claims can support RBAC, but claims can be stale until token refresh;
  1460→critical current membership/visibility should be checked in the database.
  1461→• Storage access control is implemented through policies on storage.objects.
  1462→• Service-role access bypasses ordinary RLS and therefore belongs only in narrow
  1463→trusted server/job boundaries.

  1465→Supabase Realtime, Queues, Cron, and Vault
  1466→
  1467→Official references:
  1468→
  1469→• Realtime: https://supabase.com/docs/guides/realtime
  1470→• Presence: https://supabase.com/docs/guides/realtime/presence
  1471→• Realtime authorization:
  1472→https://supabase.com/docs/guides/realtime/authorization
  1473→• Queues: https://supabase.com/docs/guides/queues
  1474→• Cron: https://supabase.com/docs/guides/cron
  1475→• Vault: https://supabase.com/docs/guides/database/vault
  1476→
  1477→Rules:
  1478→
  1479→• Authorize private realtime channels; do not broadcast tenant data on public
  1480→channels.
  1481→• Presence is ephemeral UX state, never authorization or durable truth.
  1482→• Supabase Queues is Postgres-native and suitable for durable work; still design
  1483→idempotency, retries, dead-letter handling, and observability explicitly.
  1484→• Cron schedules database functions/SQL/HTTP-triggered work; scheduled commands
  1485→must be safe to retry.
  1486→• Vault can store encrypted secrets used from database-controlled workflows;
  1487→never expose decrypted values to client queries or logs.
