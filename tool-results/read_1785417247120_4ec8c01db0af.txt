    72→    72→1. Product definition
    73→    73→
    74→    74→1.1 Vision
    75→    75→
    76→    76→AgencyOS is a configurable operating system for marketing agencies. It connects
    77→    77→the complete lifecycle:
    78→    78→
    79→    79→Lead → deal → client onboarding → campaign/project delivery → approval →
    80→    80→reporting → invoice → renewal
    81→    81→
    82→    82→Every contact, decision, task, asset, approval, hour, expense, result, and
    83→    83→relationship should belong to one coherent workspace data graph. It should feel
    84→    84→custom-built for each agency without requiring that agency to write code.
    85→    85→
    86→    86→1.2 Product principles
    87→    87→
    88→    88→1. Strong defaults, deep configuration, controlled complexity.
    89→    89→2. Agency-native concepts: retainers, campaigns, deliverables, client
    90→    90→approvals, billable work, capacity, profitability, and recurring reporting.
    91→    91→3. Database-enforced tenant isolation.
    92→    92→4. Least privilege and explicit internal/client visibility.
    93→    93→5. Collaboration for employees, contractors, clients, and reviewers.
    94→    94→6. Progressive disclosure: simple for a small agency, powerful for operations
    95→    95→teams.
    96→    96→7. Extensible through custom fields, views, templates, workflows, webhooks, and
    97→    97→APIs.
    98→    98→8. Auditable changes, especially permissions, approvals, exports, and finance.
    99→    99→9. Fast keyboard-friendly daily use.
   100→   100→10. Accessible, mobile-responsive, and trustworthy.
   101→   101→
   102→   102→1.3 Target customers and personas
   103→   103→
   104→   104→• Founder/owner: pipeline, revenue, margin, health, risk, and utilization.
   105→   105→• Sales/account executive: leads, deals, activities, follow-up, forecasting.
   106→   106→• Account manager: Client 360, requests, communication, renewals, reports.
   107→   107→• Project/traffic manager: work intake, schedules, dependencies, capacity.
   108→   108→• Strategist/creative/specialist: assigned work, briefs, files, feedback, time.
   109→   109→• Finance/operations: retainers, budgets, rates, costs, invoices, exports.
   110→   110→• Contractor: restricted project/task access.
   111→   111→• Client stakeholder: portal, requests, files, approvals, reports.
   112→   112→• Workspace admin: members, teams, roles, configuration, integrations, audit.
   113→   113→
   114→   114→1.4 Commercial quality bar
   115→   115→
   116→   116→The experience must justify a premium implementation:
   117→   117→
   118→   118→• Fast onboarding with realistic templates and demo data.
   119→   119→• Elegant information density, not a generic admin dashboard.
   120→   120→• Cross-linked records and a complete activity history.
   121→   121→• Configurable terminology, fields, statuses, pipelines, views, and branding.
   122→   122→• Safe external collaboration and client approval.
   123→   123→• Useful operational intelligence, not vanity charts.
   124→   124→• Excellent search, keyboard interaction, bulk actions, and saved views.
   125→   125→• Clear permission and audit behavior.

   452→   452→7. Tenant, identity, roles, and invitations
   453→   453→
   454→   454→7.1 Tenancy rules
   455→   455→
   456→   456→• A person has one Supabase Auth identity and may belong to many workspaces.
   457→   457→• Every tenant-owned record has a non-null workspace_id.
   458→   458→• URL workspace slugs are resolved server-side; browser-supplied workspace IDs
   459→   459→are never trusted.
   460→   460→• A workspace member may have role assignments and team memberships.
   461→   461→• Client contacts are not automatically internal members.
   462→   462→• Service-role operations are isolated to small server-only modules.
   463→   463→• All cross-entity relationships must belong to the same workspace, enforced by
   464→   464→constraints or triggers, not application convention.
   465→   465→
   466→   466→7.2 Default roles
   467→   467→
   468→   468→• Owner
   469→   469→• Administrator
   470→   470→• Operations
   471→   471→• Sales
   472→   472→• Account Manager
   473→   473→• Team Member
   474→   474→• Contractor
   475→   475→• Finance
   476→   476→• Client
   477→   477→• Guest Reviewer

   512→   512→
   513→   513→1. Authorized member enters email, role(s), optional team(s), and expiry.
   514→   514→2. Server normalizes email, checks seat/policy rules, and creates one invitation
   515→   515→transactionally.
   516→   516→3. Store only a cryptographic hash of the bearer token.
   517→   517→4. Send through an email adapter; local development writes to a capture inbox.
   518→   518→5. Recipient signs in or signs up.
   519→   519→6. Acceptance validates token hash, normalized email, expiry, revocation,
   520→   520→existing membership, and inviter authorization.
   521→   521→7. Membership/role/team creation and invite consumption happen atomically.
   522→   522→8. Emit audit and notification events.
   523→   523→9. Admin may resend with token rotation or revoke.
   524→   524→
   525→   525→Prevent invite replay, privilege escalation, duplicate membership, email-case
   526→   526→bugs, and timing-dependent partial acceptance.

   722→   722→9. Supabase security contract
   723→   723→
   724→   724→9.1 Client/session architecture
   725→   725→
   726→   726→• Browser: createBrowserClient from @supabase/ssr.
   727→   727→• Server: a new request-scoped createServerClient using the framework cookie
   728→   728→API; never share a mutable server client globally.
   729→   729→• Next.js 16: use proxy.ts to refresh auth cookies where required.
   730→   730→• Apply current Supabase SSR cache-control behavior so responses that set auth
   731→   731→cookies cannot be cached and served across users.
   732→   732→• On protected server work, validate the user against Supabase Auth; do not
   733→   733→authorize from an unverified browser payload.
   734→   734→• Validate next redirects as local allow-listed paths. Reject protocol-relative
   735→   735→and external URLs.
   736→   736→• Keep secret/service keys in server-only modules with import guards.
   737→   737→
   738→   738→9.2 Private authorization helpers
   739→   739→
   740→   740→Create a non-exposed private schema with carefully reviewed
   741→   741→security definer helpers, for example:
   742→   742→
   743→   743→```sql
   744→   744→private.is_workspace_member(target_workspace_id uuid)
   745→   745→private.has_permission(target_workspace_id uuid, permission_key text)
   746→   746→private.can_access_client(target_client_id uuid)
   747→   747→private.can_access_project(target_project_id uuid)
   748→   748→private.can_access_entity(target_type text, target_id uuid)
   749→   749→```
   750→   750→
   751→   751→Each definer function must:
   752→   752→
   753→   753→• set an explicit safe search_path;
   754→   754→• schema-qualify referenced objects;
   755→   755→• avoid user-controlled dynamic SQL;
   756→   756→• be owned by a non-login privileged role where supported;
   757→   757→• revoke execution from public and grant only what is necessary;
   758→   758→• avoid recursive RLS policy evaluation;
   759→   759→• return false for unauthenticated, suspended, or cross-workspace requests.
   760→   760→
   761→   761→9.3 RLS invariants
   762→   762→
   763→   763→Enable RLS on every exposed table, including lookup/config tables containing
   764→   764→workspace data. Policies must cover select, insert, update, and delete
   765→   765→deliberately.
   766→   766→
   767→   767→Every tenant policy must enforce:
   768→   768→
   769→   769→1. The authenticated caller is an active member of the row’s workspace.
   770→   770→2. The caller has the required action permission.
   771→   771→3. The caller satisfies entity visibility rules.
   772→   772→4. with check prevents changing workspace_id, owner, or protected state to
   773→   773→escape authorization.
   774→   774→
   775→   775→Client/guest policies additionally require an explicit portal/client grant.
   776→   776→Contractor access should be restricted to assigned/shared projects where the
   777→   777→role policy requires it.
   778→   778→
   779→   779→Never treat hidden navigation, a disabled button, or a Server Component as an
   780→   780→authorization boundary. Re-check permission in the server command/database.
   781→   781→
   782→   782→9.4 Database API hardening
   783→   783→
   784→   784→• Audit table/function grants as well as RLS.
   785→   785→• Revoke unnecessary default privileges from anon and authenticated.
   786→   786→• Expose only required schemas through the data API.
   787→   787→• Keep internal tables/functions in private schemas.
   788→   788→• Do not expose arbitrary security definer RPCs.
   789→   789→• Add rate/size limits and authorization to exports and file signing.
   790→   790→• Use server-only service-role access only for trusted jobs that cannot operate
   791→   791→under a user token.
   792→   792→
   793→   793→9.5 Relationship integrity
   794→   794→
   795→   795→For every reference between tenant-owned rows, ensure the child and parent have
   796→   796→the same workspace_id. Use composite foreign keys or deferrable constraint
   797→   797→triggers. Cover both insert and update. Include tests attempting to connect
   798→   798→records from two workspaces.
   799→   799→
   800→   800→9.6 Storage
   801→   801→
   802→   802→Use private buckets:
   803→   803→
   804→   804→```text
   805→   805→workspace-assets
   806→   806→avatars
   807→   807→imports
   808→   808→exports
   809→   809→```
   810→   810→
   811→   811→Paths must be non-guessable and begin with the authorized workspace identifier
   812→   812→where tenant-owned. Add RLS policies on storage.objects for read/upload/update/
   813→   813→delete. Validate object ownership and linked entity access. Use short-lived
   814→   814→signed URLs. Validate file size and MIME using server-observed metadata; do not
   815→   815→trust extensions. Track scan status and prevent client-visible use until safe.
   816→   816→Exports expire and are deleted by a scheduled cleanup.
   817→   817→
   818→   818→9.7 Required negative security tests
   819→   819→
   820→   820→Using two workspaces, internal users, a contractor, a client user, a suspended
   821→   821→member, and unauthenticated access, prove that:
   822→   822→
   823→   823→• no table leaks rows across workspaces;
   824→   824→• guessed UUIDs and modified slugs fail;
   825→   825→• inserts cannot claim another workspace;
   826→   826→• updates cannot move rows between workspaces;
   827→   827→• cross-workspace foreign keys fail;
   828→   828→• unauthorized role/member changes fail;
   829→   829→• a user cannot grant permissions they are not allowed to manage;
   830→   830→• client users cannot read internal comments/files/finance;
   831→   831→• contractor access is limited as configured;
   832→   832→• invitation tokens cannot be replayed or accepted by another email;
   833→   833→• signed URLs cannot be issued without entity access;
   834→   834→• search, exports, notifications, realtime channels, and reports do not leak;
   835→   835→• service-role modules cannot enter the client bundle.

   956→   956→11. Core workflows and acceptance criteria
   957→   957→
   958→   958→11.1 New agency
   959→   959→
   960→   960→1. User signs up and verifies.
   961→   961→2. Creates workspace with name, slug, currency, time zone.
   962→   962→3. Atomic transaction creates owner membership, default roles/permissions,
   963→   963→statuses, pipeline, templates, dashboard, and feature flags.
   964→   964→4. User lands in guided onboarding and may load demo data.
   965→   965→
   966→   966→Pass when partial failure leaves no orphaned workspace and another workspace
   967→   967→cannot observe any created data.
   968→   968→
   969→   969→11.2 Invite colleague
   970→   970→
   971→   971→Owner invites a teammate with role/team. Recipient accepts using the invited
   972→   972→email, joins the workspace, and sees only allowed navigation and records. Resend,
   973→   973→expiry, revoke, duplicate, changed-email, and replay behavior must be tested.
   974→   974→
   975→   975→11.3 Lead to revenue
   976→   976→
   977→   977→Import or create lead → qualify → associate contact/company → create deal →
   978→   978→advance stage with activity logging → mark won → invoke an idempotent onboarding
   979→   979→command that creates/links client, project from template, onboarding tasks, and
   980→   980→activity/audit events.
   981→   981→
   982→   982→11.4 Delivery and approval
   983→   983→
   984→   984→Create project → assign task → upload deliverable version → request approval →
   985→   985→client receives safe notification and opens portal → approve or request changes
   986→   986→→ immutable decision appears internally and externally according to visibility.
   987→   987→New version requires new approval.
   988→   988→
   989→   989→11.5 Time and profitability
   990→   990→
   991→   991→Member records billable/nonbillable time → submits timesheet → manager approves
   992→   992→→ budget burn, utilization, and projected margin update. Unauthorized users
   993→   993→cannot view costs or organization-wide time.
   994→   994→
   995→   995→11.6 Customization
   996→   996→
   997→   997→Admin adds a custom field, adds it to a form/list, enters valid data, filters and
   998→   998→exports it. Invalid values fail on both server and database-compatible
   999→   999→validation. Removing a definition is archival and does not silently destroy
  1000→  1000→historic data.
  1001→  1001→
  1002→  1002→11.7 Import/export
  1003→  1003→
  1004→  1004→Upload CSV → preview → map fields → validate → execute idempotently → report
  1005→  1005→created/updated/skipped/error rows → download error CSV. Export respects current
  1006→  1006→filters, selected columns, field-level sensitivity, permissions, and audit log.
  1007→  1007→
  1008→  1008→11.8 Portal isolation
  1009→  1009→
  1010→  1010→Client user sees explicitly shared records for their client only. They never see
  1011→  1011→internal comments, costs, other clients, workspace settings, unpublished
  1012→  1012→reports, or unshared files. Direct URL guessing and search must fail.

  1016→  1016→12. Realtime, jobs, email, and integrations
  1017→  1017→
  1018→  1018→12.1 Realtime
  1019→  1019→
  1020→  1020→Use Supabase Realtime for notification count, comments, relevant record changes,
  1021→  1021→and optional presence. Authorize private channels. Always refetch through normal
  1022→  1022→RLS-protected queries; realtime payloads are hints, not the source of truth.
  1023→  1023→
  1024→  1024→12.2 Background jobs
  1025→  1025→
  1026→  1026→Use a Postgres-native queue/outbox approach with:
  1027→  1027→
  1028→  1028→• idempotency keys and unique constraints;
  1029→  1029→• explicit attempt count and exponential backoff;
  1030→  1030→• visibility timeout/lease;
  1031→  1031→• max attempts and dead-letter state;
  1032→  1032→• structured error summaries;
  1033→  1033→• operator-visible run history;
  1034→  1034→• scheduled sweeps for stuck work.
  1035→  1035→
  1036→  1036→Use Supabase Cron for scheduled reports, reminders, recurring tasks, webhook
  1037→  1037→retries, cleanup, and queue invocation. Keep secrets in Vault/server
  1038→  1038→environment, never in job payloads.
  1039→  1039→
  1040→  1040→12.3 Email
  1041→  1041→
  1042→  1042→Define a provider-neutral interface. Local/test adapter captures messages for
  1043→  1043→assertions. Templates:
  1044→  1044→
  1045→  1045→• invite;
  1046→  1046→• magic link/auth handled appropriately by Supabase;
  1047→  1047→• mention;
  1048→  1048→• assignment;
  1049→  1049→• approaching/overdue task;
  1050→  1050→• approval requested/decided;
  1051→  1051→• weekly digest;
  1052→  1052→• report ready.
  1053→  1053→
  1054→  1054→Every email honors tenant branding, user preferences, audience visibility, and
  1055→  1055→safe deep links. Do not send email within an open database transaction.
  1056→  1056→
  1057→  1057→12.4 External integrations
  1058→  1058→
  1059→  1059→Use adapters and connection records. OAuth credentials/tokens are encrypted or
  1060→  1060→referenced through a secret store, never returned to the browser or logged.
  1061→  1061→Normalize provider webhooks to internal events. Include deterministic mocks for
  1062→  1062→local/test. A missing external account must not break core CRM functionality.

  1066→  1066→13. Reporting and metrics
  1067→  1067→
  1068→  1068→Provide role-aware dashboards:
  1069→  1069→
  1070→  1070→• Executive: pipeline, forecast, revenue, margin, utilization, client health,
  1071→  1071→overdue work.
  1072→  1072→• Sales: lead velocity, conversion, deal stage, weighted forecast, activities.
  1073→  1073→• Delivery: work by status, overdue risk, planned versus actual, capacity.
  1074→  1074→• Account: health, request SLA, approval aging, renewal, report status.
  1075→  1075→• Individual: assigned work, priorities, deadlines, logged time.
  1076→  1076→
  1077→  1077→Definitions must be explicit:
  1078→  1078→
  1079→  1079→```text
  1080→  1080→weighted pipeline = sum(open deal amount × stage probability)
  1081→  1081→win rate = won deals / closed deals
  1082→  1082→utilization = billable approved minutes / available minutes
  1083→  1083→budget burn = actual approved cost or time / approved budget
  1084→  1084→approval age = now - approval requested timestamp
  1085→  1085→```
  1086→  1086→
  1087→  1087→Filters include date range, client, project, team, owner, service, and status.
  1088→  1088→All report queries must be workspace/visibility safe. Paginate underlying detail
  1089→  1089→and constrain expensive arbitrary queries. Client report publication is an
  1090→  1090→explicit action with a snapshot/version.

  1094→  1094→14. Performance, reliability, and observability
  1095→  1095→
  1096→  1096→• Server-side pagination; never fetch whole tenant tables for lists.
  1097→  1097→• URL-backed table filter/sort/view state.
  1098→  1098→• Avoid N+1 queries and unbounded relation expansion.
  1099→  1099→• Add query indexes based on real access patterns and inspect representative
  1100→  1100→plans.
  1101→  1101→• Use optimistic UI only when conflicts and rollback are handled.
  1102→  1102→• Use version checks for concurrent approval/configuration edits.
  1103→  1103→• Dynamic authenticated responses must not enter a shared cache.
  1104→  1104→• Health endpoint reports application readiness without leaking secrets.
  1105→  1105→• Structured logs include request/correlation ID, workspace when safe, actor,
  1106→  1106→action, latency, and result; redact tokens, credentials, message bodies, and
  1107→  1107→sensitive personal data.
  1108→  1108→• Capture server/client exceptions through an adapter that is a no-op locally.
  1109→  1109→• Track audit events separately from debug logs.
  1110→  1110→• Provide runbooks for migrations, stuck jobs, webhook replay, invite problems,
  1111→  1111→storage incidents, tenant leakage response, and restore validation.
  1112→  1112→
  1113→  1113→Initial performance targets under representative seeded data:
  1114→  1114→
  1115→  1115→• common authenticated navigation: useful response within 1 second on a normal
  1116→  1116→development connection, excluding cold start;
  1117→  1117→• filtered list queries: p95 database execution target under 300 ms;
  1118→  1118→• command feedback: visible within 500 ms where no external provider is needed;
  1119→  1119→• public pages: strong Core Web Vitals and no unnecessary client JavaScript.
  1120→  1120→
  1121→  1121→Do not falsify benchmarks. Record the environment and dataset used.

  1453→  1453→Rules:
  1454→  1454→
  1455→  1455→• Enable RLS on exposed tables and write explicit action policies.
  1456→  1456→• RLS and SQL grants are complementary; RLS alone is not the whole API security
  1457→  1457→model.

  1462→  1462→• Service-role access bypasses ordinary RLS and therefore belongs only in narrow
  1463→  1463→trusted server/job boundaries.
